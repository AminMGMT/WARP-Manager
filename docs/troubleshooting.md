# Troubleshooting

## "My users aren't going through WARP"

Start here — it answers the question instead of guessing:

```bash
sudo warp-manager --diagnose      # or: WARP → Connection → Diagnose
```

It reports whether WARP, sing-box and the redirect are up; which of the two interception
paths are active with their **live packet counters**; every VPN/proxy it recognises on the
box, how its traffic leaves, and whether that path is covered.

A path marked *not intercepted* means those users keep the server's plain IP. The usual
cause is traffic that is **routed through** the box (OpenVPN, a WireGuard server, a proxy in
a bridged Docker container) rather than generated by it — set
`WARP → Connection → Client Traffic` to `all` and re-check. Details in
[How It Works](how-it-works.md#which-traffic-gets-intercepted).

If the forwarded counter stays at `0` after a client connects, the traffic is not arriving
on the interfaces being watched — the diagnose screen prints which ones those are.

## Cloudflare rate limits (HTTP 429)

Some VPS providers get a temporary **429** during WARP registration. The installer completes
anyway. Either wait a few minutes and *Restart All Services*, or import an account from a
server that already works:

```bash
sudo warp-manager --import-account /path/to/wgcf-account.toml
```

The file lives at `/var/lib/warp-manager/wgcf/wgcf-account.toml` on the working server.

---

## Selected sites fail with a TLS error

Usually the WARP tunnel has no live handshake, so routing into it black-holes those services.
The engine detects this and degrades the selected services to direct until WARP recovers —
check `WARP → Status` for the exit IP, and `Restart WARP` if it is empty.

---

## Updates

```bash
sudo warp-manager --update
```

Preserves the selected services, custom domains, white lists, WARP account, WARP+ license,
Ad Blocker settings and automation settings. Running the installer again does the same.

---

## Uninstall

```bash
sudo bash uninstall.sh
# or
sudo warp-manager --purge
```

Both run the same removal and verify it afterwards, so **no reboot is needed**. Besides the
files, WARP account and systemd units, this clears the parts that live only in the running
kernel and used to survive until a restart:

- the nftables table (and wg-quick's own)
- the policy-routing rules and tables (`51888` / `51890`)
- the `wgcf` link, even when systemd has lost track of it
- a leftover `sing-box` process holding the tproxy port
- the `route_localnet` sysctl

`net.ipv4.ip_forward` is deliberately left on — the box may be your OpenVPN or NAT gateway,
and turning it off would drop every user. `rp_filter` is left alone for the same reason: its
original value is not knowable.

Anything that could not be removed is listed instead of silently ignored:

```bash
sudo warp-manager --leftovers
```
